# Computer-Use Automation — Design Report

This project demonstrates how a system can learn a task by operating a live application, save a reviewable workflow, and run that workflow again without letting an AI model decide each browser action. The implemented target is a local banking-style website with fictional data, not a real financial system. The setup commands and demonstration steps are in [README.md](README.md).

## Architecture

The project uses Python, Playwright, Pydantic, and an OpenAI model. I chose a local web application so I could demonstrate a complete multi-step task without using real customer data or automating an external service. Playwright opens a visible browser, reads the page's accessibility-based snapshot, and performs clicks, typing, and navigation. It is still a browser-specific solution, not general desktop automation.

`app/agent/main.py` accepts a request and starts the orchestrator. The orchestrator looks for an approved matching workflow in the registry. An AI model can help choose an existing workflow and extract the request's input values; if none matches, a separate AI-guided discovery run explores the live site. During discovery, actions and observed page states are recorded. When the goal and output location can be verified, the system can shorten the candidate path by removing an action **only if the shortened path is successfully checked again**. It then builds a saved workflow as a draft. A human must approve that draft before the registry makes it available for reuse.

On a later request, the replay engine follows the approved actions in order, checks the expected page states, and reads the declared output. **The AI may select the workflow, but it does not choose replay actions.** Separate folders keep the responsibilities understandable: `discovery/` explores; `recording/` saves the observed path; `capability/` builds a reusable workflow; `registry/` stores and approves it; `replay/` executes it; `policy/` checks allowed actions; and `handoff/` transfers control to a person. 

## Artifact schema

The saved capability is a versioned JSON record validated using Pydantic, not a pasted AI conversation. `CapabilityArtifact` contains a schema version, capability ID, plain-language description, typed inputs, ordered actions, checkpoints, and typed outputs. An action records its kind and, where relevant, a control's role and accessible name, an input value, or a navigation URL. Inputs replace discovery-specific values with named placeholders such as `{{member_id}}`. Checkpoints say which action should have completed and which page route must then be present. Outputs describe how to find a particular table row and read a named column, rather than copying the balance found in the first run into future results.

The registry adds the tenant ID, application ID, separate artifact version, approval status, and a short description used for later selection. A new workflow starts as a draft; approval creates a separate approved copy. The current output extractor is deliberately limited to verified table rows and columns. Its declared output *types* describe the contract, while the current replay result returns the extracted UI values as strings; it is not a general data-extraction system.

## Determinism & error handling

Replay substitutes supplied inputs into approved actions and runs them through a fixed executor. For clicks and typing, it locates a control by role and accessible name and requires exactly one match; a missing or ambiguous control stops the step. It does not ask the model to guess a new target. Checkpoints verify expected routes, with a bounded wait for slow page changes, and output extraction checks that the requested table row and value are unambiguous. After a failure, the system does not blindly repeat a click that may already have taken effect.

`ReplayResult` distinguishes `success`, `business_outcome`, `recoverable_failure`, `needs_intervention`, and `hard_failure`. It can report the failed step, a short error code, the number of completed steps, and links to available evidence. A known missing member or missing savings account is a business outcome, rather than a software crash, when the saved rule recognizes that state. A missing input can be returned for correction; an unexpected target, failed checkpoint, or uncertain action stops or requests permitted human help. A policy violation is not something the operator can override through ordinary handoff. Recovery is intentionally conservative: the implementation has bounded checkpoint waiting and human escalation, not a general automatic retry system for arbitrary application errors.

Discovery creates a structured run log. On replay failure, the evidence recorder writes a sanitized failure report and, when possible, a page-structure snapshot; the handoff path can capture a screenshot of the live demo page. These signals help explain where a run stopped without treating a failed step as success. The required genuine discovery, replay, and exceptional-case examples must be captured from actual runs and placed in `evidence/` before submission; the supplied source snapshot does not contain those generated run files.

## Heterogeneity & multi-tenant

The current boundary between a saved workflow and the live website is the browser session and its action executor. A legacy web version could keep the same idea of inputs, ordered steps, checkpoints, and outputs, but would need a different method for finding controls when accessible names are unreliable—for example, frame-aware targeting or carefully verified visual anchors. A desktop version would need its own observation and action adapter using operating-system accessibility or screen-based control. Those adapters would also need their own target descriptions and output readers; the current role-and-name browser artifact cannot be replayed unchanged against every surface. Neither legacy-specific nor desktop execution is implemented here.

The registry already organizes records by tenant and application, but it does **not** yet share one approved workflow across institutions. A future design would keep a common workflow for a vendor application and version, then attach reviewed tenant-specific settings such as an entry URL, allowed routes, and any necessary control mappings. Each tenant would still have its own approval and safety policy. This makes reuse possible without assuming that two institutions' screens or permissions are identical.

## Escalation & handoff

When discovery or replay cannot safely continue, a handoff decision checks the type of problem, whether the existing session is usable, and whether intervention is allowed. The automation pauses while a local terminal operator works in **the same open browser session**. An intervention record identifies the run, phase, current step, reason category, session, current control owner, and available evidence. The manager marks control as belonging to the human during the intervention and returns it to automation only after the operator responds. The operator supplies a constrained summary of what was done and whether the problem was resolved; the system records the handoff states rather than pretending to capture every manual click.

A resolved response alone is not permission to continue blindly. The calling flow checks whether the live session and required page state are safe for continuation; replay checkpoint-based resumption is enabled only for the reviewed demo capability configured for it. Unresolved, cancelled, timed-out, or unverified interventions stop the run. `HANDOFF_DEMO=1` provides a repeatable, **injected** checkpoint interruption on the local read-only demo; it must not be presented as an unexpected real-world failure. A full remote operator console, independent concurrent workers, and general-purpose resumption of risky actions are outside this implementation.

## Safety

A configurable policy limits the demo to `http://127.0.0.1:8000`, approved routes, and permitted action types. The `/operations` pages and `go_back` action are blocked in the supplied configuration. Policy checks apply during discovery and replay, including checks of navigation destinations and the page reached after an action. Workflows here are read-only information lookups; a risky or irreversible banking operation is not silently approved just because an AI suggests it. Generated workflows require human review before reuse, and policy-denied actions cannot be made acceptable merely by asking for handoff.

The demo data is fictional. Replay failure reports and handoff records restrict what they persist, but this is **not a complete real-bank data-protection solution**: discovery logging can include request or page-related information, generated artifacts may contain workflow-specific values, and screenshots can reveal screen contents. Do not use real credentials or customer information in this demo or publish unreviewed evidence. A production version would require end-to-end sensitive-data filtering, protected evidence storage, access controls for approvals and operators, and clear retention rules.

## Cuts

I prioritized one working browser-based path over broad platform support. I left out native desktop control, legacy-frame-specific execution, cross-tenant sharing, a remote operator console, automatic recovery from arbitrary application failures, and general-purpose extraction outside verified tables. The saved workflow still needs a model-based selection step in the current command-line entry point, even though its **browser replay** is model-free. Candidate retrieval for a large catalog is also not implemented; the current selector handles only a limited eligible list directly. 

With more time, I would first verify the complete demo against several expected and unexpected application states and include the resulting evidence, then close the sensitive-data logging gaps. After that I would add adapter-specific control targeting, tested tenant/version overrides, and a protected operator interface. This sequence keeps the important promise of the project intact: learn against a real interface, review what was learned, and stop safely when a saved workflow can no longer be trusted.
